1. LangGraph 的取舍



用在哪里：
- 每个 Agent 可以内部使用 LangGraph（例如 ReAct 图、带工具调用的循环），其 checkpointer 用于保存该 Agent 私有的短期记忆和工具执行过程。官方文档里 per-thread persistence 正好适合这种“一个 Agent 有自己的连续对话历史”的场景。
- 如果将来需要实现复杂的 Agent 工作流（比如先规划再执行），Agent 内部可以用 subgraph 组织，但这属于 Agent 自身的设计，不涉及多 Agent 调度。

不用在哪里：
- 多 Agent 的轮流发言、举手抢麦、反驳仲裁不应该用 LangGraph 的节点和边来表达，因为这会变成一个巨大的全局状态机，图表难以维护，而且动态加入/退出 Agent、改变优先级等都不适合用固定图实现。

3. 所有后续 HTTP/WS 请求必须带 Authorization: Bearer <token>。这个 token 只在进程间传递，不写盘，保证只有当前桌面实例能访问。
4. Tauri 侧轮询 GET /health（带 token）直到 200 或超时（默认 10s），再让 WebView 加载。
5. 关闭时 Tauri 发 SIGTERM（Unix）/ taskkill（Windows），sidecar 必须捕获信号、优雅关闭所有 session、flush SQLite、退出。

为什么不用固定端口：固定 4200 会和现有 am serve 调试模式冲突，且多实例桌面应用会打架。固定端口只在"独立 localhost 调试模式"下用（保留 4200 给 CLI/自动化）。

sidecar 二进制怎么来



不用 PyInstaller（我们不是 Python）。用 Bun 的 --compile：

`bash
bun build src/server/index.ts --compile --target=bun-windows-x64 --outfile agent-meetings-server-x86_64-pc-windows-msvc.exe
bun build src/server/index.ts --compile --target=bun-darwin-arm64 --outfile agent-meetings-server-aarch64-apple-darwin
bun build src/server/index.ts --compile --target=bun-darwin-x64 --outfile agent-meetings-server-x86_64-apple-darwin
`

产出是单文件自包含可执行（~50–60MB，含 Bun runtime）。不能交叉编译，所以 Windows 二进制必须在 Windows runner 上 build，macOS 同理——这和 PyInstaller 的限制一致。

为什么不选 Node + pkg：pkg 已经不维护了；Bun compile 是当前最活跃的单文件 TS 编译方案，且 Bun 的 HTTP/WS 性能也很好（可以直接当生产 server 用）。

为什么不选 Electron：bundle 大 3–4 倍（~150MB Electron vs ~50MB Tauri），内存占用高，且我们已经有独立 server 架构——Electron 把 Node 嵌进主进程反而是浪费。Tauri 让 Rust 主进程管 sidecar 生命周期更干净。

我同意 Claude 的语言判断：基于现有仓库，核心继续使用 TypeScript。没有必须依赖 Python 的能力；LangGraph.js 只作为 Agent 内部可选执行器，不能成为共享 Session 的权威状态或调度器。桌面与 localhost 模式也应复用同一个 SessionManager，差异仅限启动、认证和生命周期适配。

但有两个实现风险要提前设门槛：

- Bun 单文件 sidecar 必须先验证 SQLite 驱动、Playwright/browser 资源、动态加载和 subprocess 行为。若兼容性测试失败，明确回退为“打包后的 Node 运行时 + JS bundle + resources”，不能到发布阶段才发现。
- Browser、CLI、插件 Agent 不应都作为主进程内的普通异步任务。API Agent 可进程内运行；Browser、subprocess 和第三方插件至少应隔离为子进程，并使用 Unix process group / Windows Job Object 管理整棵进程树。

一、共享 Session 必须是可线性化状态机



Node 事件循环本身不等于并发安全。所有异步 Agent 回调只能提交命令，不能直接修改 SessionState。建议每个 Session 一个串行 command mailbox，所有状态变更通过事件事务提交。

核心状态：

``ts
type SessionPhase =
| "idle"
| "collecting_bids"
| "arbitrating"
| "speaker_granted"
| "speaking"
| "settling"
| "paused"
| "ended";

interface SessionState {
sessionId: string;
version: number; // 等于最后提交的 seq
phase: SessionPhase;
promptEpoch: number;
activeTurnId?: string;
activeSpeakerId?: string;
contextSeq: number;
policyVersion: string;
budget: SessionBudget;
}
`

需要强制以下不变量：

1. 每个 Session 最多一个 active turn。
2. speaker.selected 只能在没有 active turn 时提交。
3. speaking 状态下可以收 Bid，但不能执行仲裁。
4. 只有 turn.completed | turn.cancelled | turn.failed | turn.timed_out 提交后，才能进入 settling/arbitrating。
5. Agent 异步结果必须携带 turnId + generation；旧 generation 的迟到 chunk 一律拒绝。
6. 取消和完成按进入 mailbox 的顺序决定：完成先提交则取消返回“已终止”；取消先提交则后续正常完成不能覆盖 cancelled。

SQLite 使用 WAL。事件追加和投影更新放在同一短事务中，按 (session_id, seq) 唯一约束。模型调用、工具调用期间绝不能持有数据库事务。

二、协议要区分 Command、持久事件和瞬时预览



建议事件 envelope 固定为：

`ts
interface SessionEvent<T> {
schemaVersion: number;
eventId: string;
sessionId: string;
seq: number; // Session 内严格递增
type: string;
actorId: string;
correlationId: string;
causationId?: string;
occurredAt: string; // 仅展示，不参与排序
payload: T;
}
`

客户端 Command 带 commandId、idempotencyKey 和可选 expectedVersion。重复提交返回第一次结果；管理类修改若 version 不匹配返回 409。

流式输出不能逐 token 写数据库，也不能只保存最终文本：

- WebSocket 可发送低延迟 turn.output.preview，它不是权威事件。
- 每 50–100ms 或达到字节阈值合并为 turn.output.chunk 并持久化，包含连续 offset。
- 最终 turn.completed 保存内容长度和 hash。
- 断线重连使用 after_seq 补事件；客户端按 seq 去重。
- 慢客户端超出发送缓存后断开并要求重连，不能无限占内存。
- SSE 作为只读兼容接口；REST 负责命令，WebSocket 负责实时事件。外部客户端如需双向 WS，可以复用同一协议。

“共享同一个权威上下文”不应实现为可任意修改的共享 dict。每次 turn.started 固定 contextSeq，Agent 看到该序号构建出的 Transcript、共享记忆和自己的私有记忆。共享记忆写入必须是带版本的 Command/CAS，而不是 Agent 直接改对象。

三、抢麦算法不能信任 Agent 自报分数



Claude 提到的问题成立：Agent 自报 bid_score 会稳定退化成所有人都报 1.0。历史“命中率”也没有可靠真值，初期不适合作为主要权重。

Bid 应结构化：

`ts
interface Bid {
bidId: string;
agentId: string;
epoch: number;
kind: "answer" | "rebuttal" | "followup" | "clarification";
replyToTurnId?: string;
confidence: number; // 仅作小权重 tie-breaker
createdAtSeq: number;
expiresAfterRound: number;
revision: number;
}
`

具体流程：

1. Human prompt 创建新 epoch 和竞标截止时间。
2. 没有发言者时，窗口关闭或所有健康 Agent 响应后仲裁。
3. 发言期间可提交针对 active turn 的 provisional rebuttal Bid。
4. 当前 turn 终止后进入短暂 settling 窗口，允许撤回或修订 provisional Bid。
5. 之后一次性校验资格、打分并选出一人。
6. 被选 Agent 必须在 grant timeout 内确认；否则撤销并选择下一候选。
7. 无 Bid、达到轮数/时间/费用上限或连续 quiet round 时结束该 epoch。

资格校验至少包括：

- Agent 仍在线、启用且未超预算；
- replyToTurnId 存在、已终止且不是自己的发言；
- Bid 未过期；
- 同一 Agent 对同一目标和 kind 只保留最高 revision；
- 默认禁止同一 Agent 连续发言，除非它是唯一候选或人类明确点名。

仲裁分数应由服务端政策产生：人类点名、声明的 capability 匹配、等待轮数、近期发言惩罚、重复内容惩罚；自报 confidence 只能占很小权重。合法 rebuttal 可有有限 bonus，但不应保证“永远高于 fresh answer”，否则系统会被反驳链劫持。测试断言也应改成“仲裁符合当前 policy version”，而不是固定反驳必胜。

连续等待达到阈值的合格 Bid可以进入同优先级档位的保留席，提供有边界的防饥饿。每次仲裁必须持久化候选集合、分数组件、policy version 和稳定 tie-break 结果，才能确定性回放。

Agent 不应看到其他 Agent 的实时出价或 rationale，避免策略性抬价；人类调试 UI 可以看到。

四、失败恢复应基于事件日志，不是 LangGraph checkpoint



对 Claude 的 sidecar 崩溃问题，我建议：

- Tauri 检测退出后最多自动重启三次，指数退避。
- 新 sidecar 打开 SQLite，从 snapshot + 后续事件重建投影。
- 若发现 turn.started 后没有终止事件，追加 turn.recovered_as_aborted，保留已有 chunk，然后再仲裁。
- 不尝试假装恢复原模型流。多数 provider 无法从精确 token 位置续传；重新调用只能作为一个新 attempt/turn，并明确显示。
- Session 标记 degraded，UI 展示恢复原因。
- 使用数据库锁及 bootId/generation 防止旧 sidecar“复活”后继续写入。

其他关键失败语义：

- Bid 超时：视为 abstain，不拖住窗口。
- Speaker 首 token 前失败：允许受限自动重试。
- 已输出内容后失败：不得静默重试，以免重复或语义分叉。
- 取消：先提交 turn.cancel_requested，触发 AbortSignal；宽限期后终止 worker/process tree，再提交终止事件。
- 数据库不可写或磁盘满：立即暂停 Session，不能继续产生不可持久化的发言。
- UI 断线：不自动取消发言；UI 只是观察者，取消必须是显式认证命令。
- 持久化 chunk 队列达到上限：对上游施加背压；若 provider 不支持背压则取消 turn，不能悄悄丢 chunk。

五、记忆边界



完整 Transcript/Event Log 是权威记录，不应因为 compaction 直接删除。摘要是带来源的派生数据：

`ts
{
sourceFromSeq,
sourceToSeq,
summary,
model,
promptVersion,
sourceHash,
createdAt
}
`

建议分层：

- Transcript：不可变事件及 turn 内容；
- Working memory：最近窗口 + 一个或多个可验证摘要；
- Shared memory：Session 范围、事件化写入、带 provenance；
- Agent-private memory：按 (user, agent, namespace) 强制隔离；
- Long-term memory：跨 Session，默认需要用户开启并支持查看、删除、TTL；
- LangGraph checkpoint：仅属于某个 Agent 实现，ID 可为 sessionId/agentId，不能反向覆盖 Session 权威状态。

回放默认只重放事件，不重新调用模型。需要“从历史点继续”时应创建带 parentSessionId + forkSeq 的新 Session。

六、安全边界需要更诚实



“subprocess + 权限限制”不等于沙箱。v1 应称为 permission isolation，除非确实实现了 OS 级隔离。

最低要求：

- Desktop sidecar 只绑定 loopback 和随机端口。
- 256-bit 启动 token 不落盘、不放 argv、日志或长期 URL。
- WebView 先通过 Tauri invoke 获取一次性 bootstrap 能力，再换取 HttpOnly + SameSite=Strict cookie；WebSocket 校验 cookie、Origin 和 Host。
- 独立 localhost 模式默认也要求 token，拒绝 wildcard CORS，并防 DNS rebinding。
- API key 不进入 WebView、Session DB、事件日志或崩溃报告。桌面模式由 Rust 侧访问系统钥匙串，sidecar 只通过受认证的私有通道按 secret reference 请求。
- subprocess 使用 argv 数组而非 shell 字符串，清理环境变量，限制 cwd、输出、执行时间和进程树。
- 插件 manifest 声明 filesystem/network/process/secrets 权限；授权与插件版本或内容 hash 绑定，新增权限必须重新确认。
- 高风险工具调用需要人类确认。工具结果和长期记忆写入都带来源，避免 prompt injection 直接升级为持久权限。
- Browser/第三方插件 worker 崩溃不能带崩核心 SessionManager。

七、迁移策略



不建议一次性重写现有 MeetingEngine：

1. 先在 feature flag 后加入事件内核和新 IAgent.bid/speak。
2. 用 LegacyAgentAdapter 将现有 respond() 包装成单 chunk 的 speak()。
3. 新 Session 使用 SQLite；现有 JSON 提供一次性导入，导入前备份并记录源文件 hash。
4. 不做 JSON/SQLite 双写，双写故障很难证明一致。

不要把 WebSocket.bufferedAmount 当核心背压机制。它只用于判断某个 UI 客户端是否太慢。

权威路径应该是：

1. SessionManager 用 for await 拉取 speak() delta。
2. delta 先进入 bounded chunk accumulator。
3. 每 50–100ms 或达到字节阈值，await SQLite 持久化 turn.output.chunk。
4. 持久化成功后再广播给 WS/SSE。
5. 每个客户端有独立 bounded send queue；慢客户端断开并用 after_seq` 重连补事件。
6. 如果 provider adapter 是可背压的 async iterator，就暂停读取；如果是不可控 callback 流，就放进 bounded channel，满了取消 turn。

原则是：数据库持久化优先，UI 实时性次之，不能为了慢客户端或不可控 provider 无限涨内存，也不能丢 chunk。

3. 共享 Session 状态机与事件协议



决策：每个 Session 一个串行 command mailbox，所有状态变更通过事件事务提交。Session 状态为显式有限状态机。

核心状态：

``ts
type SessionPhase =
| "idle" | "collecting_bids" | "arbitrating" | "speaker_granted"
| "speaking" | "settling" | "paused" | "ended";
`

强制不变量：
- 同一时刻最多一个活跃发言；
- speaker.selected 只能在无活跃发言时提交；
- speaking 期间可收集 Bid 但仲裁延迟到发言结束后；
- turn.completed / cancelled / failed / timed_out 提交后进入 settling 再决定下一轮；
- 取消与完成按进入 mailbox 的顺序判定；
- 旧 generation 的迟到 chunk 直接拒绝。

事件 envelope 固定包含 schemaVersion, eventId, sessionId, seq（session 内严格递增）, type, actorId, correlationId, causationId, occurredAt, payload。客户端命令带 commandId 和幂等 key。

流式输出不逐 token 写库；每 50–100ms 合并为 turn.output.chunk 持久化并广播。最终 turn.completed 附带长度和 hash。持久化优先于实时广播，慢客户端断开后用 after_seq 重连。

4. 抢麦/举手/反驳协议与仲裁算法



决策：服务端结构化评分，不信任 Agent 自报分数。

Bid 结构化：

`ts
type BidKind = "answer" | "rebuttal" | "followup" | "clarification";
`

仲裁流程：
1. 人类输入创建新 epoch，打开竞标窗口（默认 3 秒可配）；
2. 窗口关闭或所有健康 Agent 已提交后，进入 arbitrating；
3. 选出下一个发言者 → speaker_granted → Agent 需在 grant timeout 内确认；
4. 发言期间可提交 provisional rebuttal Bid；
5. 发言结束后进入 settling 窗口（300–500ms），只允许撤回或降级 Bid，不允许提升或换目标；
6. settling 过后一次性仲裁，资格校验、打分、选定人选；
7. 无 Bid 或达上限则结束 epoch。

仲裁分数公式：

`
score = policy_base_score(kind, capability_match, user_mention, waiting_rounds)
+ decay_penalty(recent_speaking_count)
+ (仅合法反驳: limited_rebuttal_bonus，上限 base 的 20%，且只允许反驳刚结束的发言)
+ tie_breaker(agent_confidence * epsilon)
`

用户显式点名某 Agent 时直接胜出；连续被跳过 N 轮的 Agent 获得防饥饿提升。仲裁结果包含所有分数组件、policyVersion 和稳定 tie-break 规则，持久化以支持确定性回放。

Agent 不能看到其他 Agent 的实时出价或 rationale；人类调试 UI 可以看到。

5. 记忆架构



分层设计（从底层到上层）：

| 层 | 职责 | 持久化 | 隔离 |
|---|---|---|---|
| Transcript（事件日志） | 不可变事件源，所有 turn 内容和 chunk | SQLite 主表，按 (session_id, seq) 唯一 | 按 session |
| Working Memory | 最近窗口 + 可验证摘要（带 sourceFromSeq, sourceToSeq, sourceHash, model） | SQLite，从 Transcript 派生 | 按 session |
| Agent-Private Memory | Agent 内部状态（LangGraph checkpoint 或自定义存储） | SQLite，namespace 强制 (session_id, agent_id) | 按 agent，严格隔离 |

| Long-term Memory | 跨会话持久知识 | LangGraph Store 或 SQLite 专用表，按 (user, namespace) | 用户显式开启，支持查看/删除/TTL |

constructor(private legacy: { respond(prompt: MeetingPrompt): Promise<AgentResponse> }) {}
async *speak(turn, _runtime, signal): AsyncGenerator<AgentDelta> {
const res = await this.legacy.respond(turn.prompt);
if (signal.aborted) return;
yield { type: "text", text: res.content };
yield { type: "done" };
}
async bid() { return { kind: "answer", confidence: 0.5 } as Bid; }
}

九、拒绝方案（写给实施智能体，避免走弯路）

2. 拒绝用 LangGraph 做全局 Session 状态机：动态增删 agent、变优先级、运行时仲裁不适合固定图模型；自研事件化状态机更可控、可测试。
3. 拒绝 Electron：bundle 大 3–4 倍，内存高，且我们已有独立 server 架构——Electron 嵌 Node 进主进程是浪费。Tauri 让 Rust 管 sidecar 更干净。
4. 拒绝固定端口做桌面 sidecar：多实例打架，且和 am serve 调试模式冲突。port 0 + token 握手是唯一安全方案。
5. 拒绝 agent 自报 bid_score：会稳定退化成所有人报 1.0。服务端结构化评分，自报 confidence 只作 epsilon 权重 tie-breaker。
6. 拒绝把工具调用混入 text delta 通道：隐式协议难以审计。runtime.callTool() 显式接口，SessionManager 中介鉴权。
7. 拒绝逐 token 写 SQLite：性能灾难。每 50–100ms 合并为 turn.output.chunk。
8. 拒绝 JSON/SQLite 双写迁移：双写故障无法证明一致。一次性导入 + 备份。
9. 拒绝 Redis Pub/Sub 做事件总线：桌面应用不依赖外部服务。SQLite WAL + 进程内 EventBus 足够。
10. 拒绝把 bid rationale 实时给 agent 看：策略性抬价。持久化但 visibility 隔离。

Codex 最终陈述



我确认三方已形成可实施共识，没有未解决的核心分歧。我的最终推荐是：在现有 TypeScript 仓库上增量演进，构建自研事件化共享 Session 内核；LangGraph 只作为单个 Agent 内部可选执行器；桌面采用 Tauri 2 + sidecar；P0 必须先验证 Bun compile 风险。

硬决策



1. 语言与框架
- 核心继续使用 TypeScript，不重写 Python。
- 前端：React + Vite。
- 后端运行时：Bun 优先，Node 兼容保底。
- 桌面：Tauri 2。
- 存储：SQLite WAL。
- 类型与校验：packages/protocol + zod。
- 测试：vitest + fast-check + deterministic scheduler。

2. LangGraph 边界
- 不用于共享 Session、抢麦、仲裁、全局状态。
- 仅作为单个 Agent 内部可选实现，例如 ReAct、工具循环、私有 checkpoint。
- Session 权威状态只来自自研 SessionManager 的事件日志和投影。

3. 运行时拓扑
- SessionManager 是唯一权威状态机。
- 桌面模式：Tauri 启动 sidecar，sidecar 绑定 127.0.0.1:0，stdout 输出 { port, token, bootId }。
- localhost 调试模式：同一个 createServer()，默认端口 4200，可配置 token。
- 桌面和 localhost 共享服务代码，差异只在入口、认证、生命周期。

4. Session 并发模型
- 每个 Session 一个串行 command mailbox。
- Agent、UI、工具、WebSocket 回调只能提交 command，不能直接修改状态。
- 所有状态变更必须追加事件，并在同一 SQLite 短事务内更新投影。
- 模型调用和工具调用期间绝不持有数据库事务。

5. 状态机
- 固定 phase：idle、collecting_bids、arbitrating、speaker_granted、speaking、settling、paused、ended。
- 同一 Session 最多一个 active turn。
- speaking 期间允许收 Bid，但禁止仲裁。
- 只有 turn 结束、取消、失败或超时后，才能进入 settling 和下一次仲裁。
- 迟到 chunk 必须携带 turnId + generation，旧 generation 一律拒绝。

6. 事件协议
- 事件 envelope 必须包含：schemaVersion、eventId、sessionId、seq、type、actorId、correlationId、causationId、occurredAt、payload。
- seq 是 Session 内唯一排序依据。
- Command 必须带 commandId、idempotencyKey，管理类命令可带 expectedVersion。
- 流式输出先合并为 50–100ms chunk，持久化成功后再广播。
- UI 断线后用 after_seq 补事件，不取消正在发言的 Agent。

7. 抢麦与反驳
- Agent 不可信任自报 bid_score。
- Bid 只表达结构化意图：answer、rebuttal、followup、clarification。
- 服务端仲裁分数由 policy 产生：能力匹配、用户点名、等待轮数、近期发言惩罚、有限反驳 bonus、极小 confidence tie-break。
- 合法 rebuttal 只针对刚结束的 turn，bonus 上限为 base 的 20%。
- settling 窗口默认 300–500ms，只允许撤回或降级，不允许改 kind、提高优先级或换 replyToTurnId。
- Agent 不能看到其他 Agent 的实时 Bid 或 rationale；debug UI 可以看到。

8. Agent Harness
- 新接口为 bid() + speak() + observe?()。
- speak() 返回 AsyncGenerator<AgentDelta>，支持 AbortSignal。
- 工具调用不混入文本 delta，统一通过 AgentRuntime.callTool()。
- SessionManager 负责工具鉴权、预算、审计、人类确认、超时、取消和事件记录。
- LLMAdapter 增加 chatStream()，保留 chat() 作为 collect 包装。
- 旧 respond() 通过 LegacyAgentAdapter 渐进迁移。

9. 记忆
- Transcript/Event Log 是权威记录，不因 compaction 删除。
- Working Memory 是派生摘要，必须带 sourceFromSeq、sourceToSeq、sourceHash、model、promptVersion。
- Shared Memory 通过事件化 command 写入，带版本和 provenance。
- Agent-private memory 按 (sessionId, agentId) 隔离。
- Long-term memory 默认用户显式开启，支持查看、删除、TTL。
- LangGraph checkpoint 只能属于 Agent 私有层。

10. 失败恢复
- sidecar 崩溃后，Tauri 最多自动重启三次并指数退避。
- 新 sidecar 从 SQLite snapshot + events 重建投影。
- 若存在未终止 turn，追加 turn.recovered_as_aborted，保留已有 chunk，不伪装续传模型流。
- 数据库不可写、磁盘满、SQLite IO 错误时立即暂停 Session 并退出，不能继续产生不可持久化输出。
- 已输出内容后失败，不做静默重试；新尝试必须是新 turn 或新 attempt。

11. 安全
- 这是 permission isolation，不宣称完整 OS sandbox。
- sidecar 只绑定 loopback，随机端口，启动 token 不落盘、不进日志、不放 argv。
- WebSocket 校验 token/cookie、Origin、Host，防 DNS rebinding。
- API key 不进入 WebView、Session DB、事件日志或 crash report。
- 桌面模式由 Tauri/Rust 访问 Keychain 或 Windows Credential Manager。
- subprocess 使用 argv 数组，清理 env，限制 cwd、输出、时间，并管理整棵进程树。
- 插件权限绑定 manifest 版本或内容 hash，新增权限必须重新授权。

12. 打包与发布
- 首选 Tauri 2 + Bun compile sidecar。
- P0 必须验证 Bun compile 对 SQLite、subprocess、Playwright/browser agent、动态资源路径、HTTP/WS 的兼容性。
- 若失败，回退到 Node runtime + JS bundle/resources，不改核心架构。
- macOS 必须 codesign + notarize。
- Windows 使用 Azure Trusted Signing 或等效签名。
- 自动更新使用 Tauri updater。

13. Web UI
- P0：Session Dashboard、Live Session View、Event Timeline。
- P1：Session Replay、Agent Configuration、Memory Inspector。
- P2：Provider/Key Management、Policy Settings、Debug Console。
- Replay 默认只重放事件，不重新调用模型。
- Debug UI 可查看 Bid rationale、事件 payload、状态投影、chunk 队列、sidecar 状态。

14. 测试门槛
- P0 必须有 deterministic scheduler。
- property tests 覆盖仲裁、防饥饿、rebuttal bonus 上限、speaking 期间禁止选新 speaker。
- 状态机转换表必须做合法/非法路径测试。
- 集成测试覆盖 3-agent 多轮讨论、发言中 Bid 排队、取消中途 turn、重连补事件。
- packaging smoke test 启动编译后的 sidecar 并验证 /health。
- 现有 MeetingEngine 回归测试不能挂。
